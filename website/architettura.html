Dentro Ripassa: architettura e scelte tecniche

Questa pagina non parla di cosa fa Ripassa per chi studia, ma di come è costruito. È pensata per chi legge codice: chi valuta il progetto, chi lo mantiene, chi vuole semplicemente vedere se le decisioni dichiarate sono davvero rispettate.

Stack tecnico

LivelloTecnologiaPerché
App React Native 0.81 + Expo SDK 54, React 19, TypeScript strict Un'unica base di codice per Android, iPadOS e macOS.
Dati & sync Supabase — Postgres, Realtime, Auth Metadati, sincronizzazione live tra dispositivi, autenticazione, tutto su Postgres con RLS.
Allegati Google Drive REST API (scope drive.file) I binari vivono nel Drive dell'utente, non su uno storage proprietario.
Cache locale expo-sqlite + filesystem Lettura offline dei ripassi imminenti, con rotazione automatica della finestra.
Osservabilità Sentry (@sentry/react-native) Un solo punto d'accesso nel codice; niente crash silenziosi in produzione.
Qualità ESLint 9 (flat config) + Jest + Testing Library Confini architetturali eseguibili, non solo documentati; 232 test automatici.

Model / Controller / View

Livelli separati, e verificati automaticamente

La View non tocca mai i dati direttamente, il Controller non importa mai JSX, il Model non conosce React. Questo non è solo dichiarato in un documento: quattro regole ESLint (no-restricted-imports) bloccano la build se un import attraversa un confine che non dovrebbe. Un diagramma disegnato a mano, qui, avrebbe potuto mentire — questo, per costruzione, no.

Qualità e verifica

Testato, non solo scritto

  • 232 test automatici su 20 suite: repository dati, logica pura del Model, hook del Controller, schermate principali.
  • Copertura misurata a ogni push, con soglie minime che fanno fallire la pipeline se scendono.
  • CI su GitHub Actions: lint, controllo dei tipi, test e copertura ad ogni push, non solo prima del rilascio.
  • Node fissato via .nvmrc: la build è riproducibile, non "funziona sulla mia macchina".

Sicurezza e privacy

I dati restano dell'utente

  • Riga per riga, Postgres applica Row Level Security: ogni tabella filtra su auth.uid() = user_id.
  • Due flussi OAuth 2.0 PKCE separati: identità (Supabase) e accesso a Drive, mai confusi tra loro.
  • La sessione è cifrata nel Keychain/Keystore del dispositivo, non in un archivio in chiaro.
  • I binari degli allegati non transitano mai da un server applicativo: dal dispositivo vanno dritti su Drive.
